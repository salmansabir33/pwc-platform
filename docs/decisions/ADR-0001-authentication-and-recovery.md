## 3. Recommended architecture and non-negotiable boundaries

Approved baseline: one personal account with **email/password + verified email**, using built-in Django password hashing/validators, browser Django sessions, and database-backed opaque rotating mobile credentials. Do not add an identity SaaS, JWT stack, SMS gateway, Redis or Celery solely for this slice. PostgreSQL remains the initial shared state for sessions, atomic challenges and cross-process abuse budgets. Evaluate operational performance before adding infrastructure.

Authentication proves possession of factors for a personal account, not legal identity, NGO eligibility or institutional authority:
1. The same User may hold multiple separate NGO/PWC relationships. Never create accounts per NGO or client.
2. Membership, volunteering, representative verification and grants remain separate domain records/services.
3. Verifying email/phone never verifies NGO representative authority, even for an organization-domain email.
4. PWC Board/staff titles confer no NGO-private access; Django staff/superuser is not a business authorization shortcut.
5. NGO admin grants do not imply finance view/write/approve/export rights. Step-up does not grant a missing permission.
6. Imports create unclaimed NGO records, never authenticated users; contact equality never auto-links imported records or merges accounts.
7. Recovery restores personal authentication only. It cannot appoint a representative, resurrect revoked grants, resolve disputed NGO control or bypass verification. Recovered sessions remain subject to current tenant permissions and sensitive-action assurance.
8. PWC project approval cannot commit an NGO. Authentication tokens contain no authority to bind organizations.

### Responsibilities
- `accounts`: existing User, canonical contacts, password verification, challenges, personal session lifecycle and account security services; small DRF adapters call transactional services.
- Custom email authentication backend: lookup only the approved verified canonical email, call Django password verification and validators, perform dummy hashing on unknown identities, check `is_active` and security epoch. Do not leave a second public username-login path.
- Web: Django session engine, explicit CSRF-protected login/logout and a session-status check tied to the personal session registry. DRF session defaults alone are **not** sufficient protection for an anonymous login view; enforce CSRF explicitly there.
- Mobile: narrowly scoped DRF bearer authentication for high-entropy opaque access credentials, validated against live session state on each protected request. Document and independently review this small credential service; do not invent cryptographic primitives.
- Authorization workstream (PWC-02C/PWC-03B): active tenant, per-action permissions and object ownership checks after authentication. Neither client-selected context nor cached role labels is authority.
- Security events/delivery adapter: minimal event records and durable delivery state within this work package, compatible with the later shared audit/outbox work. No broad audit platform implementation bundled into auth.

## 5. Versioned API and transport contract

All routes below have prefix `/api/v1/auth/`. This is the v1 implementation target, not a claim of deployed endpoints. Reject unknown privilege-setting fields; cap bodies/strings before hashing; accept JSON only for JSON commands. IDs and times are UUID/RFC3339 UTC strings. All auth responses (including errors) use `Cache-Control: no-store`; no proof in Location/query strings, logs or analytics. Response values below are sketches with named fields, not credentials.

### Transport selection (applies before side effects)
- **Public P:** possession of the purpose-bound challenge proves only that flow; it is not login authority. Browser unsafe requests still require explicit CSRF + exact trusted Origin checks, including anonymous registration/login/reset confirmation. Native public requests use no cookies; same proof semantics. Native link handling must use verified app links, not assume a custom URI scheme is private.
- **Web W:** Django session cookie only; server recognizes portal from trusted ingress/configuration, never JSON `client_kind`/`device_label`. Secure, HttpOnly, host-only session cookies; SameSite=Lax. Rotate Django session and CSRF token on login; rotate session key on step-up, keeping registry mapping atomic. CSRF bootstrap returns the masked token; the CSRF cookie may be HttpOnly when bootstrap JSON is used and need not be JS-readable. No parent-domain cookie sharing, browser localStorage token or wildcard credentialed CORS.
- **Mobile M:** `Authorization: Bearer <opaque_access>` only for protected requests; public mobile login/refresh carry their specified proof in JSON. No cookie fallback, no embedded client secret.
- **Both X:** shared personal-security endpoints accept exactly one valid W or M mode. Cookies require CSRF for unsafe methods; bearer mode never bypasses cookie checks by falling back.
- If a session-cookie credential and Authorization header are **both present**, reject 400 `AMBIGUOUS_CREDENTIALS` before checking either identity, updating activity or mutating anything, even if one credential is invalid. CSRF cookies alone are not a session credential. W-only rejects bearer; M-only rejects session cookies with 400 `TRANSPORT_NOT_ALLOWED`. Invalid supplied credentials never fall back to anonymous or another mode. Missing protected auth: 401 `SESSION_INVALID`; malformed/unsupported Authorization: 401. Public and session-issuance commands reject supplied Authorization headers rather than treating a bearer credential as proof of registration/reset/login; mobile refresh uses only its explicit body refresh proof. This does not forbid the single Bearer mode on protected X/M routes. P routes reject mixed credentials and never select a target account from an incidental cookie; browser CSRF is enforced independently. A browser must not use native routes to obtain a CSRF-free cookie session; native routes issue no cookies and reject browser Origin-bearing login requests (**R2**, exact native-ingress controls reviewed with web contract).

## 6. Registration, resend, reset and delivery state machines

### Flow isolation and verification
- Generate independent random `flow_id`, high-entropy flow-control secret and separate email proof using Python/Django secure randomness. Store only digests of flow controls/proofs. Use at least 256-bit CSPRNG secrets, established hash/constant-time comparison functions; never derive secrets from email, UUID or timestamps. Passwords use Django hashers, not fast token hashes.
- Request states: `pending_delivery → awaiting_proof → consumed`, with terminal `expired/invalidated`; delivery status is separate. A link may arrive before delivery acknowledgement, so a valid committed proof may confirm in pending delivery state. GET/prefetch never consumes or changes flow. Verification link uses allowlisted HTTPS origin plus fragment/app-link handoff; explicit confirmation POST carries proof, no third-party scripts or telemetry, Referrer-Policy no-referrer.
- `flow_control` returned to the requester permits resend of **that flow only**, not verification or account lookup. Email recipient can complete with flow ID + email proof without knowing the initiating device's flow control; this supports cross-device verification safely. A requester cannot set password before presenting the emailed proof.
- Resend requires exact flow ID and control digest; wrong/unknown control is generic 202, does not cancel any proof. Valid resend within cooldown coalesces with the current delivery; after cooldown, lock flow, increment generation, invalidate only its earlier proof/delivery generation and issue a new proof. Deadline remains the original 30/15-minute expiry; it never slides on resend. An expired flow requires a fresh request. Separate requests for the same email do not invalidate each other; target-wide send limits still apply.
- Registration completion locks flow, validates active generation/deadline and password, then creates one User/contact in a transaction. Database uniqueness arbitrates simultaneous flows; loser returns `CHALLENGE_INVALID` without password overwrite or a leaked duplicate-account message. No user/grant/claim is created by requests, imported records or delivery acceptance.
- Reset proof captures user, active contact ID and auth_epoch. After lock/recheck, one successful confirm sets Django password, increments epoch and recovery_generation, sets recovery hold, invalidates all user challenges/intents, revokes sessions and commits security events. Email notifications contain no secrets. Existing MFA stays enabled. Successful reset is not login, MFA removal, NGO authority recovery or grant restoration.

### Replaceable email adapter and bounded delivery
**R4 conservative target:** durable PostgreSQL DeliveryIntent dispatcher driven by a scheduled Django management command, no broker requirement. Requests for unknown/existing/noneligible targets all take the same bounded database-response path; enqueue a non-send placeholder when necessary, with indistinguishable public flow envelopes. Never synchronously wait on an external provider only for existing accounts. No promise of perfectly constant timing: test distributions and prevent account-dependent provider calls in the request path.

Use Django's in-memory mail backend for synthetic tests, console output only with synthetic addresses/proofs in an isolated developer console (never production logs). Payload needed for retries must be encrypted using a vetted library with an independently configured key ID/key, not a DB-resident key or proof digest. Hash-only challenges cannot reconstruct outgoing links. **B2** blocks encrypted dispatch until the library, key loading, rotation/decryption behavior and test configuration are reviewed; synthetic challenge logic can be developed without a live provider but cannot be declared delivery-complete.

Worker claims a due intent with a short `select_for_update(skip_locked=True)` lease, commits before network I/O, rechecks challenge generation/expiry immediately before sending, and records result in another short transaction. Never hold user/session locks while sending. Retry the **same current proof**, not an unannounced new generation. **R5:** bounded exponential backoff (1, 2, 4, 8 minutes, maximum 5 attempts including first), no attempt at/after challenge deadline. Provider success means handed off, not inbox delivery. Timeout has unknown delivery outcome: retry may duplicate the same link; do not claim exactly-once mail. Resend versus in-flight send may deliver an old link; it must remain invalid server-side. Mark stale intents cancelled/expired; delete encrypted secret payload at successful handoff/terminal state/deadline. Sent payload cannot be retried; an explicit later resend creates a new generation within original deadline. Dispatcher crash/lease expiry may duplicate a link, never duplicate a User or revive proof. Provider outage leaves public accepted response; alert internally and never bypass verification. Identity mutation success must not be rolled back solely because its notification delivery later fails.

## 7. Sessions, linearization and client lifecycle

### Concurrency contract
Use PostgreSQL READ COMMITTED with explicit locks, not process mutexes. Security transitions obey one lock order: **User → active contact/factor rows (stable ID order) → AuthSession(s) (UUID order) → challenge/credential/intent rows**. Locate a selector without mutation first to determine owner; then lock in order and re-read all conditions. Registration with no User locks its flow and relies on verified-contact uniqueness; after a collision it does not acquire another user's locks to change that account. Define deadlock retry only around a transaction before response secrets/side effects are emitted; no mail inside these transactions.

- Login verifies password, then locks User and rechecks password hash snapshot/active state/contact/epoch before creating preauth or session. If password/epoch changed, fail/re-authenticate; do not issue a session using pre-reset proof.
- Reset, password/contact change, logout-all and suspension lock User, increment epoch and revoke all sessions/challenges/intents as specified. All mutation paths, including management/support code, must use this service; toggling is_active alone still immediately denies auth, but reactivation must not revive stale credentials.
- Refresh locks User then session then refresh row. Recheck epoch, active state, hold restrictions, idle/absolute expiry and consumed state in that transaction. Reset/logout-all/suspension and refresh serialize: either refresh commits first and is subsequently revoked, or revocation commits first and refresh fails. Never issue a valid post-revocation credential from a stale check.
- Competing reset proofs lock the same User. First success advances epoch; second fails. Reset versus password/contact change similarly invalidates the older proof. Logout-all advances epoch even for callers on another device. Suspension+reactivation never restores an old session.
- Protected requests validate User/session/epoch/expiry from a coherent online DB read, no stale role/token-only cache. Reads authorized before revocation commits may finish; there is no promise to erase an already sent response. Sensitive writes and proof consumption recheck under User/session/domain locks in the **same transaction as the action**, so stale auth cannot authorize a later write. PWC-02C must integrate this boundary with tenant services.

### Idle expiration without polling keepalive
Approved idle limits are based on `last_interactive_at`, initialized at login. Every request, refresh and assurance use checks `now >= min(last_interactive_at + idle_limit, absolute_expires_at)` and rejects expired sessions before any renewal. **R6 conservative rule:** reads, polling, notifications, background refresh, `me`, session listing, client heartbeats and client-supplied “user active” flags **never** update it. Only successful explicit credential reauthentication or allowlisted user-command mutations renew idle time; server fixes the allowlist, not a query/header. A passive reader may have to reauthenticate; do not silently add a heartbeat bypass. Successful password reauthentication after expiry creates a new login session rather than resurrecting an expired session. Authenticated clients can mimic real actions, so this is not a cryptographic proof of a human gesture; absolute expiry remains the hard ceiling. Activity writes are conditional/atomic and cannot move timestamps backwards or extend absolute expiry.

### Rotation and lost response
On valid mobile refresh: consume old refresh, replace old access, increment credential generation, create exactly one current access+refresh pair in one transaction and return after commit. Consumed-token replay revokes **that session family**, not other devices, and records an event; a guessed selector with wrong secret does not trigger victim-family revocation. Expired/revoked credentials return uniform 401 without recreating a family. **R7:** no grace reuse, idempotent replay response or stored plaintext pair. A lost response after commit means the client cannot safely recover the new refresh; clear secrets and require login. If the old refresh is retried it revokes the family; do not create a second descendant. Absolute expiry never extends; refresh never updates interactive activity.

Flutter stores access in memory and refresh in vetted OS secure storage, excludes backups where supported, serializes refresh with a single-flight mutex, atomically replaces secure refresh state before releasing waiting requests and clears credentials on uncertain storage/write/rotation outcome. Retry safe reads once; non-idempotent commands need their own idempotency contract. Logout clears storage, private caches and navigation even on 401/network failure; show that server revocation was not confirmed when offline. Device listing/other-session revocation supports lost-device response. A private screen clears on context switch/revocation even though personal identity persists.

Web uses Django server-side sessions with per-portal host-only cookies, online registry/epoch checks and exact CSRF/Origin enforcement including anonymous login. No JS refresh token. Registry mapping follows cookie rotation; old session key is unusable after rotation. Same-origin proxies use relative browser URLs. Portal identity/lifetime derives from trusted routing; an NGO Web cookie does not become a PWC Operations session by changing a request field. Actual origins/proxies/headers remain O gates.

## 8. MFA, operation assurance and recovery holds

### Factor lifecycle and recovery codes
**A09 approved:** TOTP + single-use recovery codes for designated privileged actions. **R8 technical profile:** one active TOTP factor, standards-based 30-second periods, 6 digits, acceptance window ±1 timestep; atomically accept only a timestep strictly greater than factor's last accepted value. Use a vetted maintained implementation; rate-limit before factor checks. No custom TOTP or encryption. A pending enrollment expires in 5 minutes; confirmation must come from the same authenticated session with unchanged epoch/recovery generation and clear hold; only successful confirmation activates it and generates a single recovery-code set (recommend 10 independent ≥128-bit codes, shown once). Lock User/factor during confirmation, replacement/removal and code consumption. Never show an already stored factor secret or recovery code on a GET/list endpoint. Successful initial activation records the live TOTP assurance/factor revision on the confirming session, invalidates pending MFA flows and revokes other sessions. Lost code-response means rotate through authorized flow, not fetch old plaintext.

First enrollment requires recent password and a clear recovery hold. Existing-factor replacement/removal/code rotation requires password+existing TOTP. Confirming a new factor never clears a hold or grants organizational authority. Enrollment requests from a recovered/restricted session are denied, not an alternate way to regain privileges. Removal/replacement rotates factor revision, invalidates assurance/preauth proofs and revokes sessions; require fresh login. If an action policy requires MFA, removal cannot make that action password-only: deny removal while that retention requirement applies, or deny the protected actions until re-enrollment. Exact domain retention/role matrix is **B3**, default deny for privileged use.

A recovery code plus correct password is a pre-enrolled recovery credential, not name/phone/document matching. Atomically consume it, increment epoch/recovery generation, revoke sessions and set `review_required`; issue only a restricted personal session after rechecking current password/epoch. It does **not** remove TOTP, clear a hold, permit factor replacement or approve a financial action. Subsequent login can use remaining codes for restricted access. Assisted lost-factor recovery remains disabled until O5 procedures are approved. This deliberate limitation must be visible in security UI, not advertised as fully automated factor recovery.

### Recovery-assurance state machine
- `clear → restricted` on successful password reset. Capture hold timestamp and active factor ID/revision at reset; do not set holds from unauthenticated requests.
- `clear/restricted → review_required` on recovery-code login, factor-loss recovery evidence or known compromise; increment recovery generation and invalidate previous clearance/assurance intents.
- Restricted personal sessions may read/update non-security personal preferences and view their own sessions; other-device revoke/logout-all remain permitted only when their personal-assurance requirements can be satisfied (current logout needs no step-up); no contact replacement, MFA enrollment/removal, delegate changes, financial operations, private exports, commitments or support elevation. Personal recovery code use never proves NGO authority. Ordinary existing MFA users still satisfy MFA login; if all factors unavailable, use code restricted login or remain blocked.
- `restricted → clear` only by current password + live single-use TOTP from the **same active factor revision confirmed before the hold**, bound to a hold-clear intent/session/recovery generation. Recheck under lock. It clears assurance hold, not revoked grants. No proof using a new factor, a recovery code, email link or cooldown alone can clear it.
- `review_required → clear` needs an independently reviewed recovery procedure; there is **no enabled automated/public/staff override** in MVP. O5 blocks this clearance. Users with no pre-hold factor after reset cannot self-clear privileged assurance; nonprivileged personal access can continue. Role activation for such users must not bypass hold by enrolling MFA.
- Every set/clear/denial records subject, actor/service, session, previous/new state, epoch/recovery generation, reason, factor revision, intent, time and correlation ID. Any future manual clearance additionally needs approved reviewer/evidence/ticket references; clearance cannot edit contact, membership or grants in the same generic support operation.

### Session-bound, operation-bound assurance
**R9:** proof lifetime up to 5 minutes and no later than intent/session expiry. `assurance/intents` resolves a registered operation, actor, session, auth_epoch, recovery generation, explicit context (including NGO UUID), target/version and canonical command digest. Never hash/log raw password in ordinary events; request digests for secret-bearing password commands must use a keyed, purpose-separated digest kept within restricted intent storage. Cryptographic helper/library review is B2. A context supplied by the client is only an identifier; server rechecks action permission and scope.

`step-up` checks password and active TOTP where required. If that **same session** already accepted live TOTP within 5 minutes using the still-active factor revision, it may use that recorded assurance instead of reaccepting the same timestep; password must still be re-entered for credential/factor/contact changes. Recovery-code assurance never qualifies. This prevents login→immediate step-up code reuse failure without broadening factor scope. New operation proofs remain single-use even when a recent MFA observation is reused.

The intent request contains the exact proposed `command`; the server validates/canonicalizes it and computes its own digest, including context/object/version. It does not store raw new passwords or accept a client-supplied digest instead of that validation. Secret command fields exist only transiently over TLS and in the purpose-keyed digest; disable request-body capture for both intent and final-command routes. Final domain command locks/rechecks user/session/intent, epoch/hold/factor revision, operation/context/object/version/digest and current grants, consumes proof and performs action atomically. Failed validation or state conflict consumes/invalidates intent as appropriate; require a new intent for changed payload/version. Never accept proof in another session, NGO, user or action. Duplicate final submission cannot run action twice; return owned state-conflict without leaking foreign object existence. The identity service does not itself implement finance/grant/commitment commands.

Conservative designated actions: credential/contact/factor changes, logout-all/other-device revoke require fresh personal assurance; NGO role delegation, sensitive exports, finance writes/approvals, commitments and platform support elevation require current password+TOTP assurance **and** independent domain grant. Initial enrollment is the explicit password-only bootstrap exception for clear-hold users. **B3:** PWC-02C/domain owners must finalize the action/retention matrix before protected domain integrations; missing entries default deny, not broad MFA-based access. Password-reset proof is its own recovery flow, not reusable step-up.

Final contact replacement is a two-stage operation: request consumes its own recent intent; verify new address; then obtain a **new** final-replacement intent using current password+required live/recent TOTP, bound to new normalized email and challenge ID. An earlier 5-minute proof is never stretched to match the 30-minute contact challenge. **R10:** new-contact verification uses 30-minute expiry. On replacement, retire old login contact, invalidate all old-contact reset/verification proofs and prior intents, preserve User UUID/relationships, increment epoch and revoke all sessions including caller, notify both addresses. A delayed reset sent to the retired email must fail. Reassigned email ownership never transfers old user's account or NGO relationships.

## 9. Security events and abuse-control contract

Record registration completion, verification/reset request/delivery outcomes, reset success/denial, login/factor success/failure, refresh/replay, revocation/logout-all, suspension, contact/factor changes, recovery-code consumption, hold transitions, intent issue/consume/reject and rate-limit trips. Events use code/pseudonymous subject and correlation, not raw secrets or private NGO content. Authenticated events and state transitions commit together; anonymous failures use bounded separate event recording. Delivery operational events are not public account-status messages.

**R11 initial synthetic-test budgets:** login 5 failures/target/15 minutes and 30/IP/15 minutes; deliveries 1/target/minute and 5/target/hour; factor/proof 5 failures/flow; refresh 30/session/minute. Shared limits apply to existing and unknown targets uniformly using keyed canonical digests; flow retries do not reset target budgets. Do not permanently lock an account due solely to anonymous requests. Exact global budget, distributed ingress protections and shared NGO/NAT fairness need load/operational review (O2/O3); DRF's process/cache throttle alone is not brute-force prevention. Bound database row growth, prune expired flows/counters with scheduled commands, reject oversized inputs early, and never trust forwarded IP without O3-configured proxies. Missing required rate-limit storage is account-independent 503, not unlimited bypass.

**R12 synthetic retention floor:** preserve consumed refresh digests until absolute family expiry; preserve consumed challenge metadata until challenge deadline; encrypted send secrets are deleted per §6, not kept merely for audit. Production event/contact/IP retention and disposal are O4, not invented statutory periods. Synthetic TTL cleanup tests must exercise these floors and verify cleanup cannot resurrect sessions/proofs. Encrypt backups and configure secrets outside Git; actual production controls remain operational gates.
